## What it is

Two ways to stop depending on the single Microsoft-hosted agent. **Managed DevOps Pools (MDP)**: Microsoft runs VM-based agents on your behalf, in a Microsoft-owned subscription, and they register in an agent pool you configure from images that match the Microsoft-hosted ones. **Container Apps jobs + KEDA**: an event-driven Azure Container Apps job whose `azure-pipelines` KEDA scaler polls the agent pool queue; each pending pipeline job starts one container that registers an agent, runs exactly one job, and exits. Microsoft documents both as first-class patterns for Azure Pipelines agents.

The free self-hosted parallel job is a correction to the 2026-09-19 note, which framed "buy one or two extra self-hosted parallel jobs" as the first decision. It is not: the organization already has one self-hosted parallel job with unlimited minutes at no cost, automatically, with no billing setup beyond what already exists. The purchase decision only starts at the *second* self-hosted job, and only if concurrency above 1 is wanted.

## What it changes, and the catches

* **Managed DevOps Pools cannot be used today, and clearing the reason is a much bigger decision than agent hosting.** `docs/handoff.md` (session two, 2026-09-19) records that `coolhome` is a Microsoft-account-owned organization and that an Entra token from `az account get-access-token` was rejected with `TF400813`. Managed DevOps Pools' own prerequisites page requires exactly the thing that failed: "your Azure DevOps organization must be connected to Microsoft Entra ID." Checked live today, the subscription (`ac39dedd-...`) also has `Microsoft.DevOpsInfrastructure` and `Microsoft.DevCenter` both `NotRegistered` &mdash; a smaller, one-command fix, but moot until the org-level prerequisite is met. Connecting an Azure DevOps organization to Entra ID is an org-wide change (every member signs out, clears cached credentials, and gets remapped), not a setting to flip inside an agent-hosting decision. Until the platform owner decides to do that for reasons of its own, MDP stays out of scope.
* **hadolint still runs `docker run` on the agent, which breaks Container Apps jobs but not MDP.** `pipeline-templates/pipelines/extends/container-images.yml:26` runs `docker run --rm -i hadolint/hadolint:v2.12.0 hadolint ... < Dockerfile` in the Validate stage. Every actual image build already avoids Docker-on-agent (`az acr build` via ACR Tasks, `pipeline-templates/steps/container-build-push.yml`), so this is the one remaining Docker step in the templates, and the only thing standing between `container-images.yml` and running on a Container Apps job. It needs to switch to the hadolint binary (or an `az acr run` wrapper) before that pipeline can move. This was already flagged on 2026-09-19 and has not been fixed since; it would not need fixing under MDP, which is a real VM.
* **The PAT is still the only workable registration path, and it is a new long-lived secret.** The KEDA `azure-pipelines` scaler and the agent's own registration both need a PAT scoped to Agent Pools (Read & manage). Learn's alternative registration methods (service principal, Entra device code) exist, but both are Entra-identity flows, and the same organization-level gap that blocks MDP forecloses them here too. This is unchanged from the 2026-09-19 note and still contradicts ADR 0006 ("workload identity everywhere, no stored cloud secrets") on purpose; it still deserves its own ADR.

Smaller points: the build-tools image (`containers/base-images/build-tools/Dockerfile`: .NET 10 SDK, Node 24, PowerShell, GitVersion, CycloneDX) already exists and says in its own comment that it is meant to be a job container, but nothing in `pipeline-templates/` references it as one yet (`resources.containers` does not appear anywhere in the templates); wiring it in is part of this work, not already done. A Container Apps environment exists only in `dev` (`cae-mrd-dev`, from run 3985); `shared` has no Container Apps environment, so a consumption-only environment for the agent job is new platform-infrastructure work, not a parameter flip. `Meridian.VmImage` (`ubuntu-24.04`) is read from `pipeline-templates/variables/common.yml` and expands into every `pool:` block across four extends templates and five job templates; moving off it is a template-tag change with every consumer re-pinned together, exactly as ADR-governed template changes already work here.

## What it does not do

Neither option changes what a wave does or fixes anything on handoff-6's backlog: test/prod environment values, Entra app registrations for the services, a second release manager, or pruning dead template tags. It buys unlimited minutes and a cheaper path to more parallelism, not a different platform. Building the Container Apps path costs roughly the same one session the 2026-09-19 note estimated: the environment, the job, the KEDA scale rule, PAT-in-Key-Vault wiring, the hadolint swap, and a preview compile against a mirror branch before any consumer repoints to it.

## Decisions for the platform owner

1. Whether to buy additional self-hosted parallel jobs ($15/month each) to raise concurrency above 1. The first job is already free and automatic; this decision only concerns the second and further jobs.
2. Whether a rotated PAT in Key Vault is an acceptable, ADR-recorded exception to ADR 0006's workload-identity rule. Unchanged from 2026-09-19; still open.
3. Whether to connect the `coolhome` organization to Microsoft Entra ID at all, for reasons independent of agent hosting. That is the only thing that would open Managed DevOps Pools as an option here, and it is an org-wide decision, not an agent-hosting one.

## Recommendation

Do Container Apps jobs now, not Managed DevOps Pools: one Container Apps environment in `shared`, the build-tools-derived agent image, the hadolint-binary swap, a PAT in Key Vault, and a KEDA scale rule against the org's existing free self-hosted parallel job (no purchase needed to match today's parallelism of 1). Record the PAT exception in a new ADR. First milestone: `pipeline-templates-ci` plus one low-stakes consumer pinned to the new pool and green, before repointing every consumer. Do not run the dev teardown/redeploy test (handoff-6, "do next" item 4) on the new pool the first time: that script still has its own unmerged fix in flight (the `_links` wait-loop guard), and stacking a new agent platform under an unproven script makes any failure ambiguous about which change broke it. Run teardown/redeploy on the new pool only after it has carried a few ordinary waves of Microsoft-hosted-equivalent traffic. Leave Managed DevOps Pools out of scope until the owner separately decides to connect the organization to Microsoft Entra ID.
